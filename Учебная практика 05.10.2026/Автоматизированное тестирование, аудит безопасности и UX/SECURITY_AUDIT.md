# Отчет об аудите информационной безопасности и тестировании UX

## 1. Цель аудита
Комплексная проверка программных компонентов CRM-системы перед сдачей практической работы (05.10.2026):
1. Аудит защиты от атак типа SQL-инъекция (SQL Injection, CWE-89) во всех SQL-запросах;
2. Проверка корректности работы механизмов валидации пользовательского ввода;
3. Оценка отказоустойчивости при сбоях СУБД и обработке исключений (`try...except`) с выводом информативных диалоговых окон (`MessageBox`);
4. Контроль предотвращения случайной потери данных при навигации (кнопка «Назад»).

---

## 2. Анализ безопасности SQL-запросов (SQL Injection Prevention)

### Методология аудита
Были исследованы все операции доступа к данным в модуле `db_manager.py`:
- `get_all_partners(search_query)` — динамический поиск по реестру партнеров;
- `get_partner_by_id(partner_id)` — получение реквизитов контрагента по идентификатору;
- `add_partner(data)` — создание контрагента (`INSERT`);
- `update_partner(partner_id, data)` — редактирование полей контрагента (`UPDATE`);
- `delete_partner(partner_id)` — удаление партнера (`DELETE`);
- `get_partner_sales_history(partner_id)` — выборка детальной истории поставок (`JOIN`);
- `calculate_material(...)` — запросы к справочникам типов продукции и сырья.

### Результаты анализа кода:
- **Конкатенация строк в SQL**: Полностью исключена. Ни в одном запросе не используются f-строки вида `f"SELECT ... WHERE name = '{name}'"` или сложение строк `+`.
- **Параметризация запросов**: Все запросы к СУБД оформлены с позиционными плейсхолдерами `?` и передачей параметров отдельным кортежем.
  ```python
  # Пример безопасного параметризованного запроса:
  cursor.execute("""
      SELECT partner_id, partner_name, email
      FROM partners
      WHERE partner_name LIKE ? OR email LIKE ?;
  """, (f"%{clean_search}%", f"%{clean_search}%"))
  ```
- **Экранирование спецсимволов**: СУБД SQLite производит экранирование управляющих символов и кавычек на уровне парсера, что гарантирует защиту от выхода за границы строковых литералов.

### Результаты тестов безопасности (`test_security_audit.py`):
1. **Тест инъекции тавтологии (`' OR '1'='1`)**:
   - Строка поиска воспринимается буквально как текст; посторонние записи не выдаются. Тест пройден.
2. **Тест деструктивной инъекции (`'; DROP TABLE partners; --`)**:
   - Попытка выполнить составной деструктивный запрос завершается безопасным поиском текстового фрагмента; структура таблицы `partners` остается нетронутой. Тест пройден.
3. **Тест экранирования кавычек и спецсимволов при сохранении**:
   - Значения полей корректно сохраняются в базу данных как единая строка без синтаксических ошибок. Тест пройден.

## 3. Анализ обработки исключений и UX-уведомлений

### 1. Отказоустойчивость при сбоях СУБД:
- Все обращения к БД обернуты в блоки `try...except` с перехватом специализированных исключений `DatabaseConnectionError` и `DatabaseIntegrityError`.
- При сбое подключения пользователю выводится модальное окно ошибки с указанием проблемы и пошаговой инструкции (проверка прав доступа к файлу базы).

### 2. Валидация входных данных:
- Модуль `validators.py` отсекает пустые обязательные поля, некорректные email и отрицательные/нечисловые рейтинги до обращения к БД.
- В случае ошибки выводится информативный диалог `MessageBox` с рекомендациями по исправлению.

### 3. Защита от потери данных при возврате назад:
- Форма `PartnerEditWindow` фиксирует исходное состояние полей при открытии.
- При нажатии кнопки «Назад» или закрытии окна (если данные были изменены) вызывается диалог `CustomDiscardDialog` с вопросом о подтверждении выхода. Несохраненные данные не будут потеряны случайно.

Архитектура приложения и модуль доступа к базе данных полностью соответствуют требованиям информационной безопасности, надежности и эргономики интерфейса.
